# App releases and instances — design

Date: 2026-11-11. Status: draft for review. Replaces: the app deploy path
(`vetra-deploy-action`, `ci/deploy`, `ci/artifacts`, `app_deployments`,
previews), artifact channels, the licensing environment model
(`license_environments`, `stage`, template modes). Vetra Studio products are
out of scope (section 9).
Builds on: [2026-11-10 app release rollout](2026-11-10-app-release-rollout-design.md)
(its gated logic moves into rollouts here).

Vetra is in development: this is a clean break. Existing environments may be
dropped, except the customer data in section 13.

## 1. Why

What publishers mean by "an app" and what Vetra built have drifted apart:

- **No real versions.** The base version in `package.json` is never bumped.
  `main` publishes packages as `<base>-main.<run>.<sha7>` and images as
  `sha-<12 hex>`, two version lines from one push. Only a hand-pushed `v*` tag
  makes a semver, and it deploys nothing. Sektar "v1.0.9" exists only as a git
  tag; Vetra knows `sha-cac9276bc10b`.
- **Releasing and upgrading are tangled.** One action publishes and deploys.
  Channels (DEV/STAGING/LATEST) move whenever CI says so.
- **Shared customers run unreleased code.** A SHARED plan points at the app's
  production environment, which every push to `main` deploys.
- **Two runtimes.** Production runs the app's package on Vetra's platform
  Connect/Switchboard; customer instances run the app's `host` image, built on
  tags only. A customer update is the first real test of a release.
- **Three paths own environments:** CI deploy, Studio launch, licensing
  provisioning (plus the keeper), each with its own versions and statuses.
- **Overloaded words:** publish (packages, plans, stats), channel (three
  meanings), version (sha tag, semver, Studio integer), stage, artifact,
  deployment.

## 2. Vocabulary

Each word has exactly one meaning, in code, API and console.

| Word | Meaning |
|---|---|
| **App** | A GitHub repo connected to Vetra, owned by a person or an org. Has releases, templates, plans. Owns no environments. |
| **Build** | A prerelease made by every push to a release branch or a PR: `1.4.0-main.37`, `2.0.0-beta.1-next.12`, `1.4.0-pr.12.3`. Never offered to holders. |
| **Release** | An immutable published version, `1.4.0` or `2.0.0-beta.1`, made by merging a release PR. Holds the commit, notes, image, packages, requirements. |
| **Template** | What one instance consists of: the host to run, size, extra services, base domain. |
| **Plan** | What people get: name, template, access (`shared` or `own`), validity, how they get it, target release, update policy. |
| **Instance** | One running environment, built from a template and one build or release. Kinds: branch, preview, shared, own. |
| **Rollout** | Moving a plan's instances to a new target release. |

Gone: channel, stage, artifact, deployment, DEV/STAGING/LATEST, `sha-*` tags,
template mode. "Publish" means publishing a release, nothing else.

## 3. The repo and the publish flow

### Branches

- **`main`** (or the configured production branch) makes builds
  `<proposed>-main.<run>`, `<proposed>` being the version its release PR
  proposes. release-please keeps a **release PR** open on it
  ("Release v1.5.0": changelog + version bump in `package.json`), computed from
  conventional commits since the last release.
- **Prerelease branches** (`next`, `beta`, `alpha`: any branch listed as one)
  have their own release PR proposing `2.0.0-beta.0`, `beta.1`…; the
  identifier (`alpha`, `beta`, `rc`) is a setting of that branch, changeable as
  it matures. Builds: `<proposed>-<branch>.<run>`, e.g. `2.0.0-beta.2-next.12`
  while the release PR proposes `2.0.0-beta.2`. Finishing: merge the branch
  into `main`; `main`'s release PR proposes `2.0.0`.
- **Maintenance branches** (`1.x`, optional) have their own release PR for
  `1.4.2`.
- **PRs** make builds `<proposed>-pr.<n>.<run>` of their target branch's
  proposed version.

Version rules:

- Every version is semver.
- A version is a **release** when its prerelease part is empty or matches
  exactly `^(alpha|beta|rc)\.\d+$`; anything else is a **build**.
- Releases are ordered by semver. Builds are ordered only among themselves,
  by the run number of their branch or PR (section 14.17), and are never
  compared with releases: a build is never a plan's target, so nothing needs
  that comparison (semver would put `2.0.0-beta.2-next.12` after
  `2.0.0-beta.2`).

### The workflow and the action

One workflow, generated by Vetra, identical for every app, owned by the action
repo (the three copies today go): `.github/workflows/vetra.yml` runs
`powerhouse-inc/vetra-publish@v1` with `app-id` on pushes to release
branches, on PRs, and on release-PR merges. Everything else comes from the
repo's `powerhouse.config.json` (`vetra` section): release branches and their
prerelease identifiers, which host to build, package dirs, the smoke test.
In phase 1, `vetra-deploy-action@v1` stays unchanged and keeps deploying;
repos opt into `vetra-publish` (both may run side by side). From phase 2 the
old action is deprecated: it fails with a message pointing at the new
workflow.

Auth is unchanged: GitHub OIDC (audience `renown.vetra.io`) exchanged at
Renown for workload tokens; Vetra checks repo, ref and event against what is
being published.

One run:

1. **Version** — as above. On a release-PR merge the action tags `v<version>`
   and creates the GitHub release with the notes.
2. **Build** the host image once: `cr.vetra.io/<namespace>/<app>:<version>`
   (naming below). OCI labels: version, commit, repo, host (`cli`).
3. **Attest** it with GitHub artifact attestations
   (`actions/attest-build-provenance`, plus an SBOM attestation): SLSA
   provenance signed with the run's identity. For private repos GitHub keeps
   these in its own non-public log, so repo names and commits never reach a
   public transparency log (keyless cosign would publish them to Sigstore's).
4. **Publish packages** (if any) at the same version to the Vetra registry:
   builds under dist-tag `<branch>`/`pr-<n>`, prereleases under `next`,
   releases under `latest`.
5. **Report** `POST ci/releases` (below). The action deploys nothing.

### Image naming

`cr.vetra.io/<namespace>/<app>:<version>`

- `<namespace>`: the owning org's Renown handle, or the owner's handle for a
  personal app; without a handle, `u-<first 8 hex of the address>`. A handle
  rename is handled as a transfer (below). One Harbor project per namespace;
  the action gets push rights for it from `POST ci/registry-token` (below).
- `<app>`: the app's slug: **unique across all of Vetra** (it also names the
  app's instance hosts, section 5), never changes (a rename does not move
  images or hosts). A second host image of the same app is
  `<app>-<host>`.
- Tags are written once and never moved. Vetra records the digest; instances
  run by digest.
- Isolation is per namespace: an org's apps can push to each other's
  repositories. Accepted: they share admins, tags are immutable, and Vetra
  accepts a release only when its signature names the app's own repo.
- **Transfer** (between orgs, or personal → org): Vetra copies the app's
  images from `<old>/<app>` to `<new>/<app>` (a Harbor copy within one
  registry: same digests, shared layers), rewrites `image_ref` on every
  release record, then deletes the old repository. Instances run by digest
  and keep running; they pull from the new path at their next update. CI gets
  push rights for the new namespace from the transfer on.

### `POST ci/registry-token`

`{ "appId": "…" }` → `{ "registry": "cr.vetra.io", "username": "…",
"password": "…", "repository": "<namespace>/<app>", "expiresAt": "…" }`:
a Harbor robot with push rights on the namespace's project, valid for 1 hour,
issued only to the app's own CI identity (the same workload-token check as
`ci/releases`). Vetra creates the namespace's project on first use.

### `POST ci/releases`

```json
{
  "appId": "…",
  "version": "2.0.0-beta.1",
  "kind": "release",                // "build" | "release"
  "branch": "next", "pr": null,
  "run": 412,                       // the workflow run number: orders builds and releases of a branch
  "commit": "cac9276bc10b…",
  "notes": "## Features …",         // releases only: the changelog
  "image": { "ref": "cr.vetra.io/sektar/sektar:2.0.0-beta.1", "digest": "sha256:…", "host": "cli" },
  "packages": [{ "name": "@sektar/sektar", "version": "2.0.0-beta.1" }],
  "requires": { "powerhouse": ">=6.2.3", "services": ["DOCLING"], "size": "M" },
  "migrates": true
}
```

Vetra verifies the attestation through the GitHub API (built by this repo's
`vetra.yml` workflow at this commit, digest matching), stores the record
immutably and answers: 200 for a version it already has with the same digest
(a re-run is a no-op), 409 for the same version with a different digest. `requires` comes from `powerhouse.config.json` (`vetra.requires`).
`migrates` is set when the commits since the previous release add or change
files matching `vetra.migrations` (globs; default: the project's reactor and
read-model migration folders), or when the config sets `vetra.migrates: true`
for the next release.

## 4. Releases in Vetra

- **Records**: `releases (app_id, version, kind, branch, pr, run, commit, notes,
  customer_notes, image_ref, image_digest, host, packages, requires, migrates,
  scan_status, created_at)`, unique on (app, version). Builds live in the same
  table with `kind = build` and are pruned (the newest 20 per branch, PR builds
  when the PR closes). Releases are never deleted.
- **Customer notes** (`customer_notes`): what holders see. Starts as a copy of
  the changelog; the publisher edits it in the console until a rollout of that
  release is announced.
- **Scan**: Harbor's Trivy scans each image; `scan_status` is `clean`,
  `findings (n critical)` or `pending`. A rollout to customers refuses a
  release with critical findings unless the publisher overrides it (audited).

## 5. Instances

One table, `instances`, replaces `app_deployments`, previews,
`license_environments` and the licence `stage`.

| Kind | One per | Target | Admins | Removed when |
|---|---|---|---|---|
| **branch** | release branch | the newest build or release from that branch (a release-PR merge produces a release, not a build) | publisher | branch deleted |
| **preview** | open PR | that PR's newest build | publisher | PR closed |
| **shared** | shared plan | the plan's target release | publisher; members: the plan's licence holders | plan retired and no live licence left |
| **own** | holder of an own plan | the plan's target release, or a pinned one | the holder | licence ended: stopped after 7 days, deleted after 90 |

The **Team plan** is optional (off by default, one click on the app page; org
apps only): a shared plan for the owning org's own people, without codes or
grants. Its instance does not use the licence gate: it admits the org's
members, kept in sync with the org (`ACCESS=members`, the member list set by
Vetra). When it exists, a release must have run healthy on it before a
customer rollout of that release starts (section 7).

### What every instance runs

The release's host image (`ph run <host> serve`: switchboard + Connect in one
container) plus the template's extra services. Vetra sets, per instance:

| Setting | Value |
|---|---|
| `PH_HOST` | the release's `host` |
| `PH_SWITCHBOARD_DATABASE_URL` | the instance's own Postgres database |
| `/data` volume | persistent; holds the server identity, attachments, registry packages |
| `PH_WORKFLOWS_SECRETS_MASTER_KEY` | generated once per instance, kept in OpenBao |
| `PUBLIC_URL` | `https://<instance-host>` |
| `ADMINS` | per kind (table above); for publishers: the owner, or the org's admins |
| access gate | shared instances: `ACCESS=licensed`, `VETRA_APP_ID` (below); the Team instance: `ACCESS=members` with the org's members |
| `OPENROUTER_API_KEY` | from the LLM broker, capped at the plan's budget, when the plan includes AI |

Platform Connect/Switchboard services, template packages and channels are
gone: the image carries the app.

### Licence gate (Powerhouse switchboard)

Today a host knows only "signed in" and `ADMINS`. A shared instance must admit
licence holders only. New switchboard access mode, in the Powerhouse monorepo's
host/switchboard auth: with `ACCESS=licensed` a caller must be an admin or hold
a live licence for `VETRA_APP_ID`, checked against Vetra's `hasLicense` and
cached for 60 s. A lapsed licence loses access at the next check. This is the
one change outside Vetra's repos.

### Instance hosts

`<app>-<kind-name>.<base domain>`: `sektar-main`, `sektar-next`,
`sektar-pr-12`, `sektar-starter` (shared: the plan's slug), `sektar-team`, and
generated names for own instances (`calm-bat-b4qzzqbb`) unless the holder sets a
custom domain. App slugs are unique across Vetra, so these never collide
between orgs; plan slugs are unique within their app, and `main`, `team` and
`pr-<n>` are reserved.

## 6. The reconciler

One loop replaces CI deploy, licensing provisioning and the
keeper. For each instance:

1. **Desired state** = template + target (an image digest) + the settings
   above.
2. **Compare** with the environment document; on a difference, apply: create
   (from the warm pool when one fits), update, stop, delete.
3. **Status**: `pending`, `updating`, `ready`, `failed (reason)`, `stopped`.
   `ready` requires the health check to pass **and** the running digest to
   equal the target.

A failed create or update leaves the instance on its previous digest. An
instance whose plan cannot render (a service Vetra cannot run, a requirement
the template does not meet) shows `failed: plan can't be provisioned`, never a
silent wait. Instances are rendered whole from the template (no "floor").

Targets move as follows: branch instances on every build or release reported
from their branch; preview instances on every build of their PR; shared and
own instances only through a rollout.

## 7. Plans and rollouts

### Plans

`{name, slug, template, access: shared|own, validityDays, issuers,
targetRelease, policy, noticeHours}`. Issuers are how people get it (invite
codes, publisher grants; payment providers plug in here later). "Free" and
"Conference 2026" on one community instance are one plan with two issuers.

**Policy** decides whether new releases roll out by themselves:

| Policy | Rolls out by itself |
|---|---|
| `manual` (default) | nothing |
| `patches` | `1.4.0 → 1.4.1` |
| `minor` | `1.4.x → 1.5.0` (majors wait) |
| `follow <branch>` | every release from that branch (Team, Early access) |

A major release never rolls out to a `manual`, `patches` or `minor` plan by
itself.

### A rollout

A rollout moves one or more plans to a release (e.g. Starter and Pro to
`2.0.0`). Started by the publisher (changing plans' targets) or by a plan's
policy (then for that plan alone).

1. **Check** the release's `requires` against each plan's template, the scan
   status, and, when the app has a Team instance, that the release has run
   healthy on it (the Team plan itself is exempt). Refuse with the reason
   before anything moves.
2. **Rehearse** (when the release `migrates`, or on request): clone one
   customer instance, its database and `/data` included, into a throwaway
   instance; update the clone; run health checks and the repo's smoke test
   (`vetra.smoke` in `powerhouse.config.json`: a command run against the
   clone's URL). A failure stops the rollout before any customer is touched.
3. **Announce**: holders get an in-app notice and an email with the customer
   notes and the date (`now + noticeHours`). Holders may "update now".
4. **Update one instance at a time**: the rollout's shared instances first,
   then its own instances (a plan is either shared or own). Before each: a **backup** (database + `/data`). After each:
   health and the error rate compared with before; a regression **pauses** the
   rollout and alerts, as does a failure.
5. **Paused**: retry, skip that instance, or roll back.

**Pinning**: the publisher can pin an own instance to a release; rollouts skip
it and show it as "pinned at 1.4.2".

**Rollback**: setting the target back. For a release that `migrates`, rolling
back an instance restores the backup taken before its update (data written
since is lost; the console says so before the click). Otherwise it swaps the
image.

Backups are also taken daily for shared and own instances (kept 14 days) and
can be restored from the console.

## 8. Rebuilds for base-layer fixes

The host image locks Node, Powerhouse and OS packages, so a security fix
reaches customers only through a new release. Vetra tracks the Powerhouse
version and base image each release was built with. When a fix is published:

- Vetra opens a PR in each affected app's repo bumping the dependency (as
  Dependabot does), titled `fix(deps): …` so release-please makes it a patch.
- Its merge produces a patch release; plans on `patches` or `minor` roll it
  out by themselves.
- Apps whose newest release is affected and has not been rebuilt within 14
  days are flagged on the app page and in release health.

## 9. Vetra Studio

Out of scope. Studio products keep their current path (`launchStudioVersion`
→ `app_deployments`, integer versions) until they get their own design; this
spec's removals apply to apps published from GitHub only.

## 10. Permissions and audit

| Action | Who |
|---|---|
| Publish a release | whoever may merge the release PR (GitHub) |
| Edit customer notes, start/pause/roll back a rollout, pin, change plans, override a scan | the app's owner, the org's admins, or members with the **release manager** role |
| Turn on the Team plan, add templates | owner and org admins |

Every action above, plus every release reported and every instance status
change, goes into an **audit log** per app: who, what, when, from where
(console, API, policy). Shown on the app page; kept 1 year.

## 11. Console

- **App page**: Releases (version, date, notes, which plans run it, scan,
  provenance), Instances (branch and preview instances with URLs and status),
  Plans (each with its target, "2.0.0 available", **Roll out**), Audit log.
- **Release health**: per app, which instances run which version, rollout
  progress, paused and failed instances, pinned instances, upcoming notices,
  outdated base layers. The landing view for a publisher.
- **Rollout view**: the steps of section 7 live, with pause/retry/skip/roll
  back.
- **Instances** show provenance: "built from `sektar@v2.0.0`, commit `abc123`,
  signed by GitHub Actions".
- **Environments page**: the publisher's instances grouped by kind; a holder's
  own instances under their licences.
- **GitHub**: Vetra comments the preview URL on each PR and reports a check
  with the instance status.
- **Public `/apps`**: each app's current release, last updated, and its
  changelog.
- **Notifications** (Discord, Slack, email per org): release published,
  rollout started/paused/finished, instance failed, rebuild needed.

## 13. Switch-over

Test apps: dropped and recreated (their repos get the new workflow PR).

**Sektar's customer instances** (licensed environments with real data) are
carried over:

1. Freeze: no rollouts on Sektar during the switch-over.
2. For each licensed environment: `pg_dump` of its database and a copy of its
   `/data`, stored in the backup bucket with the holder and licence recorded.
3. Sektar publishes its first release through the new action.
4. For each holder: the new `own` instance is created on that release, the
   dump and `/data` restored, the holder told the new URL (their custom domain,
   if any, moved). The old environment is kept stopped for 30 days, then
   deleted.
5. Shared access (Sektar's SHARED plans) moves to a new shared instance; no
   data to move (it pointed at production).

## 14. Operational requirements

1. **The action runs as the Vetra GitHub App.** Release PRs, tags and GitHub
   releases are created with the app's installation token, never the
   workflow's `GITHUB_TOKEN` (GitHub starts no workflows for what that token
   creates, so a release PR would get no preview and its merge would publish
   nothing). The GitHub App needs `contents: write` and
   `pull_requests: write`.
2. **Publisher and holder settings.**
   - Publisher secrets, settings and files per template (e.g. Sektar's Google
     OAuth client JSON mounted at `/client_secret_sektar-web-app.json`,
     `SEKTAR_OAUTH_RELAY_BASE`), stored in OpenBao, the same on every instance
     of the template. Names Vetra sets itself (section 5) are refused.
   - Holder settings on their own instance (their own OAuth client, custom
     domain), kept per instance and applied on every update and rollback.
3. **Withdrawing a release.** The publisher can withdraw a release: no plan
   can target it, rollouts to it stop, instances still on it are flagged in
   release health. Release records are never deleted.
4. **Deleting an app with holders.** With live licences: holders are told
   with a notice period (default 30 days), may download their backup, then
   their own instances go through the end-of-licence steps. Without live
   licences: deleted at once.
5. **Holder data stays the holder's.** The publisher controls updates,
   rollbacks, backups and logs of own instances, but has no access to their
   data unless the holder grants support access (time-limited, audited).
   Holders can download a backup of their own instance at any time.
6. **Registry retention.** Build images are deleted with their build records.
   Release images are kept while any release record or instance needs them.
7. **Healthy** means: the switchboard's health endpoint answers, Connect
   serves its page, the reactor has finished its migrations, and the version
   the host reports equals the target. The reconciler, rehearsals and the
   regression pause all use this definition.
8. **Update windows per plan** (e.g. nights and weekends, Europe/Berlin):
   after the notice, a rollout updates customer instances only inside the
   window. "Update now" by a holder ignores it.
9. **Vetra's own canary app.** A small test app publishes, releases and rolls
   out through the whole pipeline every night on staging; a failure alerts
   the Vetra team.
10. **`ph vetra check`** validates the `vetra` section of
    `powerhouse.config.json` and prints the version the next release would
    get, before anything is pushed.
11. **Minimum Powerhouse version.** Publishing needs a project with a host
    (`hosts/cli`, uniform runners on). `ph vetra check` and the publish action
    report what is missing; Vetra opens a PR adding `hosts/cli` to a connected
    repo that lacks it.
12. **Rehearsals never expose holder data.** The clone has no publisher in
    `ADMINS`; the smoke test runs inside the cluster with a service identity;
    only pass/fail and logs without data leave it; the clone is destroyed
    right after.
13. **Preview cost.** At most 5 preview instances per app (configurable; the
    oldest PR's preview is removed first). Branch and preview instances sleep
    when idle (the housekeeping service) and use a single Postgres instance
    without S3 backups.
14. **Licence gate availability.** When Vetra cannot be reached, the gate keeps
    a caller's last positive answer for 24 h; callers never seen before are
    refused.
15. **GitHub permission upgrade.** Release PRs need the Vetra GitHub App's
    `contents: write` and `pull_requests: write`; an installation without them
    blocks publishing, and the console shows the approval link.
16. **Backups use CNPG.** The backup before an update is an on-demand CNPG
    backup to S3 (each instance's Postgres is a CNPG cluster with S3 backups
    already); restoring is CNPG point-in-time recovery to that backup, plus the
    `/data` volume snapshot taken with it.
17. **Newest** build or release of a branch (and newest build of a PR) is the
    one with the highest workflow run number, never the one that arrived last.
18. **PR titles.** Vetra's PR check fails a PR whose title is not a
    conventional commit (squash merges make the title the commit, and
    release-please versions from it).

## 16. Removed

`vetra-deploy-action` (after the alias period), `ci/deploy`, `ci/artifacts`,
`ci/registry-credentials` (replaced by a namespace push token), `deployApp`,
`rollbackApp`, `app_deployments` and previews tables for GitHub apps (Studio keeps its
path),
`license_environments`, the licence `stage`, artifact versions and channels on
the app document, template modes, template packages, `templateHash`
re-templating, the floor logic, the keeper's provisioning, per-app Harbor
projects, Sektar's root `Dockerfile` and its conditional `fusion-dockerfile`.

## 17. Out of scope

Multi-region or HA instances; a holder choosing their own version; moving data
between shared and own instances; approval workflows beyond permissions;
billing and paid plans (they arrive as a new issuer); custom domains for shared
instances; several Vetra apps in one repo; usage metering; a public status
page; Vetra Studio products (section 9).

## 18. Build order

Each phase ships on its own and is usable.

1. **Publish**: `vetra-publish` action (branches, release PRs, versions, host
   image, naming, packages, `ci/releases`, signing, `requires`, `migrates`;
   acting as the Vetra GitHub App, 14.1); `releases` table recording each
   release's Powerhouse version and base image; Releases view; `ph vetra
   check` (14.10). Old deploy path still running.
2. **Instances**: `instances` table, reconciler, branch and preview instances,
